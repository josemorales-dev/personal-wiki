Read the BigQuery tables, not the views

Issue #187 in st-migration-scripts. This change is step 1 of 4: it adds a switch. With the switch off, nothing changes.

Where this sits in the migration

What the switch does

BigQuery has two copies of each table: a view (users) and a table behind it (users_tbl). The table is faster to read. Either way, the data lands in the store under the same name, so the reconcilers see no difference.

Switch off (default, today)
Switch on (readAnTables = true)

The rollout

  1. 1
    Add the switch (this change, built and checked, not committed yet)
    Needs: commit, pull request, review, merge, deploy. The switch stays off, so prod is unchanged.
  2. 2
    Turn it on in develop
    Needs: set readAnTables: true in the develop reconcile_all inputs in Windmill. Run the sync and compare row counts with a view-based run. No code change.
  3. 3
    Turn it on in prod
    Needs: the same input change in the prod workspace, after develop runs clean. No code change.
  4. 4
    Remove the view path
    Needs: a small cleanup pull request. It removes the switch, always reads _tbl, changes the table list to list the _tbl tables, and updates docs/architecture.md, which still says "views".

Risks to watch in step 2

Not yet tried against real BigQuery

  • The sync settings (partition keys, column lists) were written for the views. If a _tbl table has different columns or partitioning, the sync fails with the switch on. It fails loudly; it does not copy bad data.
  • The full test suite needs the shared test database. It could not run on this machine. CI runs it on the pull request.
